# GatherUp 功能全流程梳理（给非技术读者）

> 更新时间：2026-07-23
> 线上地址：https://gather-up-moirahoumikis-projects.vercel.app
> 说明：本文按「参与者 → 组织者 → 管理员」三个角色，把每条链路从头到尾走一遍，标注每个功能点的实际状态。
>
> 状态图例：
> - ✅ 完整可用：有界面、有逻辑，能真实跑通
> - ⚠️ 半成品：主体能用，但缺关键一环（会说明缺什么）
> - 🔲 只有 UI 占位：界面在，点了没有真实逻辑
> - ❌ 缺失：产品上应该有，但现在没有
>
> 一个重要背景：GatherUp 的收款方式是「线下转账 + 上传付款截图 + 组织者人工核对」，**不接微信支付/支付宝在线支付**。这是刻意的设计（面向社团、同好圈的小型活动），下文的"支付"都指这套截图核对流程。
>
> 另一个背景：站点有「演示模式」和「真实模式」两种形态。没配数据库时走演示模式——所有数据是内置的示例数据，报名、发布等操作只保存在你自己的浏览器里，不会真正写入服务器。目前线上是演示模式。

## 一、参与者链路（普通用户报名参加活动）

### 1. 注册与登录
| 功能 | 路由 | 状态 | 说明 |
|---|---|---|---|
| 邮箱注册/登录 | `/login` | ✅ | 支持真实账号（配置数据库后）和演示账号一键登录 |
| 新人引导（起名、领 GatherUp ID） | `/onboarding` | ✅ | 注册后设置昵称和专属 ID（GU-开头），ID 改名有次数限制 |
| 未登录访问受保护页自动跳转登录 | 全站 | ✅ | 访问「我的」「组织者」等页面会被带去登录页，登录后跳回原页 |

### 2. 发现活动
| 功能 | 路由 | 状态 | 说明 |
|---|---|---|---|
| 活动广场（列表浏览） | `/` | ✅ | 首页即活动广场，卡片展示活动名、城市、时间、费用、名额 |
| 搜索 + 城市/分类筛选 | `/` | ✅ | 页面内即时筛选，无需刷新 |
| 活动详情页 | `/events/[id]` | ✅ | 展示时间地点、费用模式、名额进度、报名截止时间、组织者信息、退款规则 |
| 场地库浏览 | `/venues`、`/venues/[id]` | ✅ | 可以按场地看它办过/将办的活动 |

### 3. 报名 / 下单（核心流程，共 7 步）
入口：活动详情页 →「报名」按钮 → `/events/[id]/register`

| 步骤 | 做什么 | 状态 | 说明 |
|---|---|---|---|
| ① 选身份 | 确认以参与者身份进入 | ✅ | |
| ② 时间数调 | 投票选自己能来的时间段 | ✅ | 组织者发起活动前先"数调"（摸底大家什么时候有空） |
| ③ 地点投票 | 投票选偏好地点 | ✅ | |
| ④ 等待开放 | 数调期结束前的锁定态 | ✅ | 组织者敲定时间地点后才开放正式报名 |
| ⑤ 正式报名填表 | 填昵称、人数、自定义问题（如"预计到达时间"） | ✅ | 支持组织者自定义表单字段；支持一单多人（带同行人） |
| ⑥ 上传付款截图 | 线下转账后传截图，备注「订单号+昵称」 | ✅ | 免费活动跳过此步；截图存云端存储 |
| ⑦ 等待确认 / 选座 | 组织者核对通过后，开放选座（如果活动需要选座） | ✅ | 确认前不占座、不发电子票，防止未付款先占位 |

- 名额满时可加入**候补队列** ✅：有人退出后组织者可发"转正邀请"，参与者在有效期内确认即可补上（超时自动过期）。
- ⚠️ 注意：演示模式下走的是本地模拟流程，数据只存在浏览器里；真实模式需要数据库账号。

### 4. 我的活动 / 票夹
| 功能 | 路由 | 状态 | 说明 |
|---|---|---|---|
| 我的活动总览 | `/me` | ✅ | 待审核数、待选座数、候补邀请数、历史订单一目了然；含账号资料管理（改 GatherUp ID） |
| 订单详情 | `/me/orders/[订单号]` | ✅ | 状态时间线（报名→上传付款→组织者确认→选座/签到）、金额、参与人、付款记录全都有 |
| 电子票 / 核销码 | 同上 | ✅ | 付款确认后生成核销码 + 二维码数据 + 微信群二维码（确认前刻意不展示群码，防止没付款先进群） |
| 在线选座 | 订单详情页内 | ✅ | 确认后开放；选座有临时锁座机制，超时自动释放 |

### 5. 取消 / 退款
| 功能 | 状态 | 说明 |
|---|---|---|
| 申请退款 | ✅ | 订单详情页发起，填原因和金额 |
| 退款全流程跟踪 | ✅ | 状态机完整：申请 → 组织者同意/拒绝 → 线下打款 → 上传打款凭证 → 参与者确认收款/提出争议。每一步在订单页可见 |
| ⚠️ 退款到账 | ⚠️ | 打款本身在线下（微信/支付宝转账），平台只做流程记录和凭证存档，不碰钱 |

### 6. 通知
| 功能 | 状态 | 说明 |
|---|---|---|
| 站内通知（铃铛） | ✅ | 页面右上角铃铛，未读红点、一键全部已读；**仅真实账号可用，演示模式铃铛不拉取数据** |
| 邮件通知 | ⚠️ | 后端有发邮件能力（接了 Resend 服务），但哪些事件会触发邮件、参与者能否管理订阅，目前没有成体系的配置，覆盖面有限 |
| 组织者公告 | ✅ | 组织者可对活动内成员发公告，参与者在站内收到 |

## 二、组织者链路（办活动的人）

### 1. 入驻与认证
| 功能 | 路由 | 状态 | 说明 |
|---|---|---|---|
| 组织者工作台 | `/organizer` | ✅ | 登录即可进（无需先认证），看到行动队列：几笔付款待核对、几个活动待配置 |
| 主办身份认证 | 工作台内认证面板 | ✅ | 提交主办资料 → 平台管理员审核 → 通过后获得认证标识 |

### 2. 创建活动（7 步向导）
入口：工作台 →「创建活动」→ `/organizer/events/new`

| 步骤 | 做什么 | 状态 | 说明 |
|---|---|---|---|
| ① 基础信息 | 活动名、公开 ID、场景分类、流程模板、城市、说明 | ✅ | 有 6 种场景（同好/校园/会议/聚会/工作坊/市集）和 6 种模板（基础报名/收款/选座/签到/分时预约/记录型） |
| ② 组织者 | 主办 ID + 协作组织者及权限（联合主办/财务/现场/只读） | ✅ | 协作者需在管理台确认加入 |
| ③ 场地数调 | 设候选时间、候选地点；一键复制群公告/链接/生成二维码 | ✅ | 专为"先在微信群摸底"的真实场景设计 |
| ④ 费用财务 | 免费/收费/AA，票价、结算说明 | ✅ | 只有单一票价，**没有多票档**（如早鸟票/普通票分开卖） |
| ⑤ 报名订单 | 人数上限、截止时间、是否允许一单多人、订单编号规则、自定义表单 | ✅ | 自定义表单用 JSON 配置，对非技术组织者不够友好 ⚠️ |
| ⑥ 收款座位 | 上传收款码、微信群码、付款说明；配置座位（排数 × 每排数） | ✅ | 座位图截图"自动识别"是演示假功能 🔲——点了固定生成 6排×12座，界面也标明"下一版继续做" |
| ⑦ 确认发布 | 发布前自检清单（6 项），全过才能发布 | ✅ | 有草稿自动保存/恢复，中途关页面不丢 |

- ⚠️ 演示模式下"发布"只保存在本地浏览器；真实模式会写入数据库并进入平台审核。

## 三、管理员链路（平台方）

路由：`/admin`（审核工作台）

| 功能 | 状态 | 说明 |
|---|---|---|
| 活动上架审核 | ✅ | 组织者发布的活动先进平台审核，通过后才对参与者可见 |
| 主办认证审核 | ✅ | 审核组织者提交的认证资料，通过/驳回 |

| 定时任务 | ✅ | 每天自动清理过期锁座、过期候补邀请（需配置密钥） |
| ❌ 用户管理 | ❌ | 没有封禁用户、处理举报的界面 |
| ❌ 内容管理 | ❌ | 没有下架已发布活动、编辑违规内容的入口 |
| ❌ 平台数据看板 | ❌ | 没有全平台的活动数/用户数/交易额统计 |

## 四、当前体验最明显的短板（产品判断）

按建议优先级从高到低：

### 1. 演示模式与真实模式的边界对用户不透明（优先级：高）
线上目前是演示模式：参与者"报名成功"、组织者"发布成功"其实都只存在自己浏览器里，换个设备就没了。界面提示藏得比较深，普通用户会误以为真的报上名了。
**建议**：要么尽快切到真实数据库模式上线，要么在全站顶部挂一条醒目的"演示环境，数据不会保存"横幅。

### 2. 自定义报名表单要写 JSON（优先级：高）
创建向导第 ⑤ 步让组织者直接编辑 JSON 代码来配置报名问题，这对目标用户（社团干部、同好群主）几乎不可用。
**建议**：改成"添加问题"式的可视化表单编辑器（选类型、填标题、勾选必填）。

### 3. 通知覆盖不成体系（优先级：中高）
关键节点（付款被确认/驳回、候补转正邀请、活动时间敲定）主要靠参与者自己回来刷订单页。站内铃铛只对真实账号生效，邮件通知只有零散能力，没有"哪些事件必发什么通知"的完整清单。候补邀请有有效期，错过就作废——这种强时效事件没有可靠触达是硬伤。
**建议**：先把 4-5 个关键事件的站内+邮件双通道通知补齐，候补邀请优先。

### 4. 没有多票档（优先级：中）
一个活动只能一个价。早鸟/普通/学生价、不同权益的票种是活动工具的常见刚需，现在只能靠组织者开多个活动绕过去。
**建议**：向导第 ④ 步支持添加多个票档（名称+价格+限量）。

### 5. 座位图"截图识别"是假功能，且管理后台缺内容治理（优先级：中）
座位识别点了永远生成 6排×12座，虽然界面有说明，但容易让组织者期待落空——不如先收起来只留手动配置。管理员侧只能审核"入口"（活动上架、主办认证），对已上架的违规活动、问题用户没有任何处置手段，平台一旦真实运营会立刻遇到。
**建议**：假功能先下线或明确标注"即将上线"；管理后台补"下架活动"和"停用账号"两个最小处置能力。
